Architecture plan

Rowcall Runtime and App Split

This plan describes how Rowcall should evolve from one beta codebase into a monorepo with a Python-owned runtime and a TypeScript-owned app. The goal is a standalone Python execution tool, with the canvas app acting as the human-friendly editor and runtime client.

Python source is canonical Sidecar is editor metadata Python owns execution TypeScript owns the app Monorepo first

Target shape

A Rowcall document is a real Python file that can be validated and run without the canvas. The app edits that file through a structured source-aware workflow.

Decisions

Design Principles

These rules define the boundary. When implementation details are unclear, prefer the choice that keeps execution independent from the editor and keeps the Python file meaningful on its own.

Python source is the executable truth

A .py Rowcall document must be complete enough for rowcall validate and rowcall run without opening the app. The app may hold unsaved source text, but runtime behavior starts from source plus document path.

Sidecars are app metadata

A .rowcall.json sidecar stores editor-only details such as canvas position and descriptions. The runtime ignores it by default so CLI, agents, and CI can run the Python file alone.

Python owns runtime semantics

Python owns parsing, validation, graph planning, execution, previews, copying rules, the public CLI, and the worker protocol. TypeScript asks Python for runtime answers.

The app is a structured editor

The canvas app should become a source-aware editor. It derives a graph view from Python source, applies user edit intents back to source, then reparses source to refresh app state.

Strict documents are acceptable

Rowcall documents are not arbitrary Python programs. They use a recognizable top-level structure with @node functions and top-level depends_on calls.

Monorepo before repo split

The target is a cleaner monorepo with package-shaped boundaries. A future separate runtime repo is possible, but not part of this migration.

Target

Architecture Overview

Runtime and app communicate through explicit source and protocol boundaries. The same Python runtime can serve local CLI runs, local app sessions, and later cloud-hosted execution.

Python Document

analysis.py contains nodes, outputs, and depends_on edges. It is executable without the app.

->

Python Runtime Package

Parses, validates, plans, executes, streams events, and exposes rowcall CLI plus a worker protocol.

<->

TypeScript App

Serves the browser UI, edits source and sidecar metadata, and requests runtime work from Python workers.

Canonical runtime input

Every runtime request should include source text and an absolute documentPath. The path provides __file__, traceback filenames, working directory, sidecar location, sibling imports, and cache context.

Local CLI flow

rowcall run ~/Desktop/analysis.py --json
  read source from documentPath
  parse source without import side effects
  validate and plan
  execute with cwd = document directory
  print JSON result

Local app flow

Browser canvas edit
  app rewrites Python source
  app sends source + absolute documentPath
  Python worker parses and runs current source
  TS server translates runtime events to browser UI

Runtime

Python Runtime Responsibilities

The runtime should be useful on its own. A user, script, CI job, or agent should be able to validate and execute a Rowcall document without launching the canvas app.

Load Accept source text plus absolute document path, or read source from file for CLI.
Parse Use AST parsing to decode strict Rowcall syntax without import side effects.
Validate Report duplicate IDs, cycles, missing nodes, invalid outputs, and unsupported Python shapes.
Plan Produce a deterministic dependency order for graph and target runs, with cache-aware single-node planning to follow.
Execute Run nodes in namespace isolation, copy declared outputs downstream, and emit previews.

CLI commands

rowcall validate path/to/document.py
rowcall run path/to/document.py --json
rowcall run path/to/document.py --to build_customer_facts --json --trace
python -m rowcall run path/to/document.py --json

The public CLI is Python-owned. Existing Deno tasks may remain only as wrappers to the Python CLI.

Execution context

  • documentPath is required and should be absolute.
  • cwd is scoped to the document directory during a run or session operation.
  • __file__ resolves to documentPath.
  • The document directory is temporarily available for sibling imports.
  • Pathless untitled documents are not supported for execution in the local beta.

Namespace isolation is not process isolation

Nodes execute in fresh namespaces within a runtime process, but process-global side effects can still exist. Cloud execution will require sandboxing and resource controls outside this local runtime boundary.

App

TypeScript App Responsibilities

The app remains the product experience for humans. Its job is to make the Python document understandable, editable, and runnable through a canvas UI.

Source-canonical editing

The app should treat source text as canonical. It may maintain graph state for rendering and interaction, but structural changes should become source rewrites followed by a parse refresh. 

source text
  -> parse through Python document API
  -> render graph in UI
  -> user edit intent
  -> Python source rewrite
  -> parse again
  -> updated graph

Sidecar scope

The sidecar remains valuable, but only for editor state that does not affect execution.

  • Node positions
  • Descriptions
  • Collapsed or selected state, if needed later
  • Canvas preferences

Documents can live anywhere local

The local app should support opening and running documents outside the repo, such as files on the Desktop. The local server should stay bound to 127.0.0.1 so arbitrary local filesystem access is not exposed over a network.

Protocol

Worker Protocol

The app server should communicate with a long-lived Python worker using newline-delimited JSON over stdin/stdout. Each line is one complete JSON message.

NDJSON example

{"type":"run_started","runId":"r1"}
{"type":"run_plan","steps":[{"nodeId":"load_orders","dependsOn":[]}]}
{"type":"node_started","nodeId":"load_orders"}
{"type":"node_completed","nodeId":"load_orders","result":{"ok":true}}
{"type":"run_completed","ok":true}

Initial operations

  • validate_source: parse and validate source.
  • inspect_source: return parsed document model for UI.
  • plan_run: return deterministic execution plan.
  • run_graph: execute the full graph.
  • run_to_node: execute upstream dependencies and target.
  • clear_session_cache: clear in-memory cached outputs.
  • shutdown: close the worker.
Choice Decision Reason
Worker lifetime One Python worker per active runtime session Supports cache and rich in-memory Python objects without one process per node.
Run request payload Send full source and absolute document path each run Prevents stale worker state and supports unsaved app edits.
Cancellation Kill and restart worker initially Simple, reliable, and acceptable for beta.
Streaming to browser TS server translates worker NDJSON to browser SSE Keeps browser API stable and hides subprocess details.

Plan

Migration Phases

The migration should avoid a big rewrite. Each phase creates a usable checkpoint with tests before the next layer moves.

Phase 0

Record architecture decision

Keep this plan and optionally add a short ADR. The core decision is that Python source plus document path is the canonical runtime input.

  • Target Shared understanding before code motion.
  • Output Architecture doc and migration checklist.
Phase 1

Python parser, model, validator, and planner

Move document semantics into Python modules. AST parsing should decode @node, literal outputs, function parameters, source ranges, and top-level depends_on calls.

  • Produce an ExecutableDocument model.
  • Validate strict document shape without importing user code.
  • Plan full graph and run-to-node orders.
  • Use existing examples plus targeted fixtures as regression tests.
Phase 2

Python runtime executor

Extract execution behavior into rowcall.runtime. Keep namespace isolation, display events, stdout/stderr capture, output previews, table previews, and type-aware copying.

  • Execute from source plus absolute document path.
  • Set scoped cwd, __file__, and document-directory import context.
  • Support stateless run results first.
  • Preserve current behavior where it is intentionally part of the runtime contract.
Phase 3

Python public CLI

Make rowcall and python -m rowcall the public runtime interface. Convert the Deno CLI task to a thin wrapper so there is only one runtime behavior.

  • rowcall validate path.py
  • rowcall run path.py --json --trace --to target
  • Clear exit codes for usage, validation, and execution failures.
  • Document that the CLI ignores sidecars by default.
Phase 4

Worker protocol and session runtime

Add the NDJSON worker used by the app server. The worker owns the runtime session cache and handles one operation at a time.

  • Define protocol version and message schema.
  • Support parse, inspect, plan, run, clear cache, and shutdown.
  • Send source and path on each run to avoid stale document state.
  • Use worker termination for initial cancellation semantics.
Phase 5

TypeScript server adapter

Replace TS-owned runtime execution with calls to the Python worker. Keep browser routes and UI expectations stable where it helps implementation, but do not preserve legacy response shapes just for compatibility.

  • Create a worker client in the app server.
  • Translate Python runtime events to existing or revised browser responses.
  • Use Python parser for document inspect/load as soon as practical.
  • Keep local server bound to 127.0.0.1.
Phase 6

Python source rewrite APIs

Move source editing into rowcall.document.rewrite. The first implementation supports constrained body/output edits and depends_on changes. Full node creation, deletion, and save-time app integration remain follow-up work.

  • Edit node bodies and declared outputs under strict constraints.
  • Add and remove depends_on lines.
  • Next: add, rename, and delete nodes through the Python rewrite layer.
  • Next: normalize Rowcall-managed regions while preserving unrelated top-level code.
Phase 7

UI source-canonical migration

Update the app so run requests are source-backed first, then continue migrating edit/save flows until graph state is fully derived from Python source. The current bridge renders the editable document model to source on run requests when raw source is not already available.

  • Sidecar remains app metadata only.
  • Run graph and run-to-node requests send current source text or a rendered editable document plus absolute path.
  • Next: canvas edits call Python source rewrite APIs, then the app reparses source and refreshes UI state.
  • Next: save conflict checks still compare disk revision before writing.
  • Dirty source can run before save, using the backing document path.

Implementation

Subagent Work Plan

This section is intentionally more detailed. The coordinator should use it to spawn subagents with clear boundaries and prevent parallel work from producing incompatible abstractions.

Agent A First

Python document parser and planner.

  • Create or reorganize rowcall.document.
  • Parse from source text and document path.
  • Decode nodes, outputs, parameters, source ranges, and edges.
  • Validate strict format without importing user code.
  • Return deterministic plans for graph and target runs.

Deliver tests before downstream agents build on the model.

Agent B Parallel with A

Test fixture design.

  • Promote examples into parser/planner fixtures where useful.
  • Add small synthetic fixtures for edge cases examples do not cover.
  • Define expected node IDs, edges, target resolution, and plans.
  • Include relative path fixture coverage.

Should avoid depending on unstable runtime response details.

Agent C After A

Python runtime executor.

  • Move execution behavior behind rowcall.runtime.
  • Keep namespace isolation and output-copy behavior.
  • Preserve display, stdout, stderr, warnings, and previews.
  • Execute with scoped cwd, __file__, and import path.

Agent D After A/C

Python CLI and packaging.

  • Add rowcall console entry point.
  • Add python -m rowcall.
  • Implement validate/run/options/exit codes.
  • Convert Deno CLI implementation into a thin Python CLI wrapper.

Agent E After C

Protocol and worker session.

  • Define protocol messages and versioning.
  • Implement NDJSON worker loop.
  • Add session cache and clear-cache operation.
  • Provide predictable failure messages for malformed protocol input.

Agent F After E

TypeScript server adapter.

  • Create Python worker client.
  • Route inspect/validate/run requests through Python.
  • Translate NDJSON events to HTTP/SSE responses.
  • Keep UI changes minimal during this step.

Agent G Later

Python source rewrite APIs.

  • Implement add/update/delete node operations.
  • Implement add/remove edge operations by rewriting depends_on.
  • Preserve unmanaged source where possible.
  • Add round-trip and conflict tests.

Agent H Later

UI source-canonical editing.

  • Make graph view derived from parsed source.
  • Call Python rewrite APIs for structural edits.
  • Run current source text without autosaving.
  • Keep sidecar writes scoped to editor metadata.

Coordinator rule

Do not run parser, executor, CLI, protocol, app adapter, and source rewrite migration all at once. Parser and fixture design can run in parallel. Most other work should be sequenced behind stable Python document and runtime interfaces.

Testing

Verification Strategy

The migration should use both small unit fixtures and the existing examples. Existing examples are valuable because they represent real product workflows, but they should be supplemented where they do not cover edge cases.

Example-based regression tests

  • examples/hello_world.py: smallest working dependency chain.
  • examples/polars_orders.py: third-party dataframe preview behavior.
  • examples/ecommerce/analysis.py: branching and multiple inputs.
  • examples/transit_reliability/challenge.py: larger realistic document.
  • Optional new fixture: document outside repo with relative data files.

Targeted unit fixtures

  • Duplicate node IDs and duplicate function names.
  • Cycles in depends_on.
  • Conflicting upstream output names.
  • Invalid decorators and non-literal outputs.
  • Direct node function calls rejected inside node bodies.
  • Missing declared outputs at execution time.

Candidate commands

python -m unittest
python -m rowcall validate examples/hello_world.py
python -m rowcall run examples/hello_world.py --json
python -m rowcall run examples/ecommerce/analysis.py --to build_customer_facts --json --trace
deno task cli validate examples/hello_world.py  # wrapper smoke test
deno task cli run examples/hello_world.py --json  # wrapper smoke test
deno task build

Commands will evolve as the migration lands. The important rule is that changed runtime behavior must be covered from the Python CLI before app integration depends on it.

Risks

Risks and Guardrails

These are the failure modes most likely to make the migration confusing. Treat them as design constraints during implementation.

Risk Guardrail Verification
Two different runtime behaviors Python owns parse, validate, plan, and execute. Deno CLI is wrapper only. Python CLI tests become canonical.
App graph diverges from Python source Graph state is derived from parsed source. Structural edits rewrite source and reparse. Round-trip tests and UI save/load tests.
Relative paths break for documents outside repo Runtime requests include absolute documentPath; execution cwd is document directory. Fixture with data files outside repo root.
Long-lived worker executes stale source Send full source and path with each run request initially. Dirty-source run test where disk and UI source differ.
Source rewriting damages user code Normalize only Rowcall-managed regions; preserve unrelated top-level code where possible. Golden source rewrite fixtures.
Cloud concerns overcomplicate local beta Keep local runtime simple; design protocol so worker host can later be remote. No cloud-only abstractions required for local app.

Future cloud fit

A future cloud version can replace the local Python worker with a remote sandbox worker while keeping the same app-to-runtime shape: source plus document path context, parse, validate, plan, execute, stream events. Multiplayer should sit above this at the document editing layer, not inside the Python execution engine.

This document is a planning artifact for the Rowcall beta. It favors clear runtime/app ownership before any future repository split.
