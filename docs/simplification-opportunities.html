Simplification audit · companion to the architecture explainer

Keep the core. Trim the edges.

Rowcall’s central model is coherent. The best beta work is not a rewrite. It is a short pass that removes obsolete routes and duplicate contracts, closes a few visible seams, and gives document and run state clearer owners.

Recommended posture: take the low-risk deletions and boundary fixes now. Stage the Browser Workspace extractions later. Keep the careful save transaction and current worker model until beta evidence justifies a larger change.

Beta-pragmatic Evidence-backed Few focused changes No app code changed

01 / ASSESSMENT

A good core with too many surrounding representations.

Most complexity does not come from the graph model. It comes from compatibility paths, repeated protocol shapes, and browser state that crosses several owners.

Overall judgment Suitable for an invited beta After a small confidence pass; no production-hardening program is required.
Deno tests 124 passed Backend, launcher, worker bridge, save, and security behavior.
Python tests 144 passed 2 skipped locally; parser, rewrite, runtime, previews, and CLI.
UI tests 52 passed Useful unit/state tests, but no rendered browser journey.
Strong center

One semantic authority

The Python Core owns inspection, validation, rewrite, planning, execution, and previews. That is the right place for Python meaning.

Main complexity

Repeated edges

Old HTTP and worker commands, duplicate TypeScript types, two sidecar rewriters, and multiple execution-state paths widen the mental model.

Risk balance

Do not simplify file safety

The Document Coordinator is large because it protects user Python from stale overwrites and interrupted two-file saves. Keep its behavior.

How to read this audit: the numbered opportunities simplify architecture. The later quality-fix section lists bugs and confidence gaps. A test or bug fix can be urgent without being an architectural simplification.

03 / OPPORTUNITIES

Six changes worth considering.

Each item states the recommendation, the concrete change, why it matters, and a stopping condition. Expand the agent brief if you want to delegate it.

01

Delete the compatibility shell before it becomes a promise.

Recommendation: remove old paths that have no in-repo production caller, after one final private-caller check.

Effort: low–mediumRisk: lowPayoff: high clarityConfidence: high
Grade A · do now

Current state

  • /run-node duplicates /run-to-node.
  • /runtime-session/clear-cache is a no-op.
  • rowcall update exists only to report that updates are not implemented.
  • An unused whole-document decoder occupies document.ts:451 to the end.
  • Several worker verbs have only test callers.

What changes

Remove each zero-caller feature as a vertical slice: route or command, Deno wrapper, worker verb, Python session method, types, tests, and docs. Keep the active operations decoder and the two real run modes: run through a step and run the graph.

Why it matters

The code currently suggests three execution modes, cache management, an update system, and a whole-document JSON write model. None is real product behavior. This is the best time to delete them because beta users have not built on them.

Done when: every remaining public command, HTTP route, and worker verb has a known product caller.

Evidence: document.ts:451 · main.ts:834 · main.ts:1066 · launcher.ts:357 · python_worker_client.ts:12 · browser calls only execution.ts:200

Agent brief: inventory and remove the compatibility surface 
Inventory every non-test caller of POST /run-node, POST /runtime-session/clear-cache, the `rowcall update` and `doctor --updates` paths, `decodeRowcallDocument`, and every Python worker operation. Separate real product callers from tests and documentation. Produce a keep/delete table first. Then remove only zero-caller surfaces in vertical slices, including types, tests, and docs. Preserve /run-to-node, /run-graph, document inspection/rewrite, table queries, shutdown, and the Python core functions they use.
02

Give the document contract one TypeScript definition and one metadata owner.

Recommendation: consolidate the raw document and operation types; resolve fields that no longer have a product meaning.

Effort: low–mediumRisk: lowPayoff: high clarityConfidence: high
Grade A · focused cleanup

Current state

The server and Browser Workspace define separate RowcallDocumentV1 and DocumentOperation unions. Python and Deno both apply sidecar metadata operations. A title field crosses Python, TypeScript, the API, and sidecars, but the UI labels steps from functionName and never emits a title update.

What changes

  • Move the raw TypeScript contract to one shared pure module.
  • Let either Python or Deno—not both—own sidecar operation application.
  • For beta, remove custom title unless it is intentionally restored to the UI.
  • Stop sending generated runtimeCode to the browser if no UI behavior needs it.

Why it matters

One edit currently has several opportunities to drift between languages and projections. A small field matrix and one-owner rule are enough; a schema generator or monorepo reorganization is not needed.

Done when: a raw document field is defined once in TypeScript and each persisted metadata operation has one authoritative implementation.

Evidence: document.ts:3 · UI documents.ts:55 · documentTypes.ts:3 · python_document.ts:478 and :1465 · rewrite.py:544

Agent brief: build the contract field matrix 
Build a field matrix for the server RowcallDocumentV1, the UI raw document, RuntimeGraph, DocumentOperation, the Python app document dictionary, and sidecar metadata. Mark where each field is produced, consumed, dropped, derived, or rewritten. Recommend a minimal consolidation: one shared raw TypeScript contract, one sidecar rewrite owner, and an explicit keep/remove decision for title and runtimeCode. Do not introduce code generation or change save semantics.
03

Make one path authoritative for a run plan and a final result.

Recommendation: remove duplicate work on both sides of the worker boundary without changing the SSE experience.

Effort: mediumRisk: low–mediumPayoff: mediumConfidence: high
Grade B · next

Current state

The Runtime Worker calls plan_run to emit run_plan, then execute_source parses and plans the same source again. In the browser, the final SSE event stores the response, then the mutation onSuccess stores the same response again.

What changes

Let the execution path emit its own authoritative plan, perhaps through an on_plan callback. In the Browser Workspace, make the Run Session the only owner of terminal response storage; mutation completion should only finalize transport and active-run cleanup.

Why it matters

This reduces two subtle forms of duplication: two parse/plan error paths in Python and two final-state writers in React. It keeps progress streaming, which is useful for slow beta runs.

Done when: one parse produces the plan used to execute, and one browser reducer/path records the final response exactly once.

Evidence: worker.py:221 → executor.py:106 · useExecutionSession.ts:166 and App.tsx:413

Agent brief: create one run lifecycle 
Trace one streamed run from worker request through run_plan, node events, terminal SSE, fetch resolution, React mutation onSuccess, and useExecutionSession. Propose the smallest behavior-preserving change that (1) parses and plans source once, while still emitting run_plan before node_started, and (2) stores a terminal ExecutionResponse once in the browser. Preserve SSE event shapes, cancellation, result freshness, notifications, and non-streaming API behavior. Add focused regression tests before refactoring.
04

Extract Browser Workspace state by ownership, not by file size.

Recommendation: create a real Document Session first, then make the Run Session the complete execution owner, then split Inspector modes.

Effort: medium–highRisk: mediumPayoff: high maintainabilityConfidence: high
Grade C · stage it

Current state

App.tsx is 2,900 lines and owns document load, edits, save/revision/reload, disk polling, graph transformations, run orchestration, notices, and shell UI. InspectorPanel.tsx is 3,587 lines and mixes modes, previews, trace UI, local drafts, and its exported shell. A query hook imports display-state types from the Inspector component.

What changes

  1. Move domain display-state types out of React components.
  2. Extract useDocumentSession: document, path, revision, pending operations, save state, disk state, edit/save/reload.
  3. Move run start/stream/finish/failure behind the Run Session.
  4. Split Inspector into Develop, Overview, Results, and shared preview primitives.

Why it matters

This gives future agents an answer to “where does this state belong?” The objective is not smaller files by itself. It is one write owner for document state and one for execution state.

Done when: App composes sessions and views; it no longer implements their state machines.

Evidence: App.tsx:130 · InspectorPanel.tsx:3281 · reversed type dependency at useExecutionSession.ts:7

Agent brief: propose a safe extraction sequence 
Draw an ownership table for every state value and mutable ref in App.tsx and useExecutionSession, plus the local state families in InspectorPanel.tsx. Propose a four-PR extraction sequence. Start with type movement and useDocumentSession; preserve all current revision, external-change, unknown-save-outcome, result-freshness, and network behavior. State the public contract for each extracted module and the focused tests that lock behavior before each move. Do not rewrite the UI or persistence model.
05

Decide whether input copying is a guarantee or best effort.

Recommendation: resolve this semantic mismatch deliberately; do not hide it inside a refactor.

Effort: mediumRisk: product behaviorPayoff: semantic honestyConfidence: high
Grade D · decide

Current state

The product model says branches receive copies and do not affect one another. The Preview Engine has special copy handlers for common data types, then tries deepcopy. If either copy fails, it passes the original object by reference and adds a warning.

Two honest choices

  1. Fail closed: stop the downstream step with a clear input-copy error.
  2. Best effort: keep the fallback, but describe branch isolation as best effort and make the warning prominent.

For the stated product promise, fail closed is cleaner. It may reject advanced custom objects.

Why it matters

A first sibling can mutate a shared fallback object before a later sibling runs. This is uncommon for supported DataFrames, but it touches Rowcall’s central “branch without interference” story.

Done when: a regression test and the runtime contract agree on copy failure behavior.

Evidence: product claim at 01-product-scope.md · implementation at previews.py:698 · current contract acknowledges reference fallback at 02-runtime-contract.md

Agent brief: characterize branch isolation 
Build a regression test where one root returns a mutable custom object whose __deepcopy__ raises and two sibling nodes consume it. Prove whether the first sibling can affect the second. Confirm supported behavior for normal containers, Pandas, Polars, and NumPy. Compare a fail-closed input_copy_error with the current pass-by-reference warning. Recommend one contract and list the user-visible error/documentation changes. Do not add serialization or process isolation.
06

Keep the long-lived Runtime Worker for beta; revisit only with evidence.

Recommendation: document the process boundary now. Consider a run-scoped worker later if cross-run state or memory retention becomes a real tester problem.

Effort: highRisk: highPayoff: uncertainConfidence: medium–high
Grade D · defer

Current state

One Python process handles successive runs and retains the Latest Result Store. To honor “fresh run,” the Execution Engine contains substantial local-import and bytecode invalidation logic. Process-wide modules, builtins, native state, and background threads can still persist.

Possible later model

Start a new worker for each run, then keep that worker alive only as the successful result-inspection session. Starting the next run replaces it. This could simplify import freshness and strengthen cross-run isolation, but it changes startup, cancellation, table inspection, and concurrency behavior.

Why defer

The current model is clear enough for trusted invited users, and it supports interactive tables naturally. A redesign before beta would spend risk without evidence.

Revisit when: testers report stale imports, cross-run state, runaway memory, or worker crashes that materially hurt use.

Evidence: shared worker at executor.ts:40 · import invalidation at executor.py:172 · Latest Result Store at session.py:18

Agent brief: compare worker lifecycles without implementing 
Compare the current long-lived Runtime Worker with a run-scoped worker that remains alive only to serve the latest successful result set. Map impacts on import freshness, startup cost, cancellation, child-process cleanup, table paging, latest-result replacement, direct API concurrency, and memory. Estimate which current code could be deleted and which new lifecycle state would be required. Do not implement. Recommend measurable beta signals that would justify the change.

04 / QUALITY FIXES

Small seams worth closing before or during beta.

These are not reasons to delay indefinitely. The first two bundles are short, high-confidence work. The last two buy debugging and release confidence.

UI

Make basic Browser Workspace controls tell the truth.

  • Ctrl/Cmd+S while editing code: the UI advertises the shortcut, but the Canvas handler excludes CodeMirror and the editor keymap defines only Shift+Enter. A browser Save Page action can win.
  • Initial invalid file: status polling starts only after a successful load. Repairing an invalid startup file requires a browser refresh because the error view has no Retry action.
  • Read-only contract: it is currently latent because Python always reports false, but node dragging and Save do not honor it. Remove the unused contract or enforce it everywhere.

Evidence: Canvas.tsx:230, InspectorPanel.tsx:1582, App.tsx:186, App.tsx:1201, App.tsx:1728

Recommendation

Add one application-level save command, add Retry to initial load failure, and make one explicit decision on document-level read-only. These are small fixes with direct user impact.

API

Make the local API fail predictably and fail closed.

  • The three run routes call c.req.json() without catching malformed JSON and then access properties without first requiring a plain object. Invalid requests can become unstructured HTTP 500 responses.
  • Authentication exempts static GET files, then protects a manual list of API prefixes. A future route that is not added to the list fails open.
  • The server prints its token-bearing URL; the launcher tees that output into ~/.rowcall/logs/rowcall.log.

Evidence: main.ts:231, :834, :899, :961, :101, launcher.ts:1755

Recommendation

Add one shared run-request decoder, require auth for everything except explicit public static GET paths, and redact the token from persisted logs. Keep Host and Origin checks.

DX

Make debugging point to the user’s real source.

Rowcall slices node function text and removes excluded globals lines before compiling them with the original filename. That restarts line numbering at 1. A reproduced exception on source line 13 reported line 2; a globals exception on line 9 reported line 1.

Also, generated projects ignore .venv and Python caches but not Rowcall’s persistent lock and transaction/temp patterns. Opening a new project can immediately create an unexplained untracked lock file.

Evidence: parser.py:957, :988, executor.py:521, :587, launcher.ts:119, python_document.ts:1216

Recommendation

Preserve line offsets with blank padding or adjusted AST locations and add exact-line tests. Copy the repository’s Rowcall save-control patterns into the new-project .gitignore.

TEST

Add two journeys, not a broad test program.

The suite strongly covers functions and several process/file boundaries. It does not render the app in a real browser. The installed-release smoke runs outside the checkout, but uses an explicit clean Python and exercises headless new, validate, and run, not the actual managed environment or visual app.

  1. Browser smoke: load fixture → edit in CodeMirror → save with shortcut → run through step → see output.
  2. Packaged environment smoke: outside checkout, exercise managed setup and one starter-library document; assert the materialized requirements file removed editable-install lines.

Evidence: app/ui/deno.json:3, smoke-installed-release.sh:78, ci.yml:22

Recommendation

Keep both as release or one-platform integration checks if dependency installation makes them slow. Do not pursue broad screenshot coverage or a full test pyramid for this beta.

Known and acceptable for invited beta: no Python sandbox, no server-enforced time or memory limit, one active document, one serialized Runtime Worker, unsigned/unnotarized macOS binaries, manual publishing, and no compute cache. State these limits; do not build production infrastructure around them yet.

05 / KEEP

Complexity that earns its place.

Removing these would make the system shorter and less trustworthy. Preserve the behavior even if code is later moved into smaller modules.

Python as the canonical document

It remains reviewable in Git, runnable without the UI, and directly editable by people and agents.

Python-owned semantics

Do not reimplement Python parsing, validation, rewrite, planning, or execution rules in TypeScript.

Semantic operation batches

They express user intent and avoid blind whole-file replacement from a browser projection.

Revision-bound save and run

They protect changes made by an external editor or agent and bind execution to visible source.

Unknown save-outcome lock

It prevents a second write from replaying an operation batch that may already have committed.

Atomic source/sidecar recovery

The Document Coordinator’s journal, locks, temp files, fsync, and alias checks protect real user work.

Strict document grammar

The constraints are what make safe AST inspection and visual source rewriting understandable.

Fresh runs with no compute cache

It is the simplest behavior to explain and avoids provenance and invalidation work during beta.

Bounded previews

Rich Python values stay in Python; browser payloads and user-defined representation hooks are controlled.

Latest Result Store

Keep one provenance-checked result set for table paging. Name it as inspection state, not cache.

Host, Origin, and token checks

Simplify the token rule to fail closed, but keep all three protections around local code execution.

One active document and run

This matches the invited-beta scope. Do not introduce sessions, registries, queues, or multi-user ownership yet.

06 / SEQUENCE

A practical order of work.

Stop after any wave if the beta feels reliable and the next wave does not solve an observed problem.

WAVE 0 · HOURS

Close obvious beta seams

Fix the code-editor save shortcut, malformed run bodies, auth default, token logging, and generated .gitignore. Add Retry to the initial load error if time permits.

Stop gate: a tester can open, edit, save, and receive a predictable error without a misleading control or persisted token.

WAVE 1 · 1–2 PRs

Delete false product surface

Inventory private callers, then remove the unused full-document decoder, compatibility run/cache paths, unimplemented update path, and confirmed zero-caller worker verbs.

Stop gate: each public command, route, and worker verb describes real beta behavior.

WAVE 2 · DAYS

Add two confidence journeys and repair tracebacks

Add one browser smoke and one packaged managed-environment smoke. Preserve source line numbers in runtime exceptions.

Stop gate: the shipped path works end to end, and a failure points to the correct user line.

WAVE 3 · STAGED

Consolidate ownership

Unify document contracts and sidecar ownership. Parse/plan once. Store final run results once. Extract Document Session, then complete Run Session ownership, then split Inspector modes.

Only start if: ongoing agent changes are repeatedly hard to locate or regress across duplicate paths.

LATER · EVIDENCE

Debate semantic and process boundaries

Choose fail-closed versus best-effort copying. Revisit the long-lived worker only if real beta use shows cross-run state, memory, or freshness problems.

Do not prebuild: caching, sandboxing, multi-document sessions, collaboration, or distributed execution.
