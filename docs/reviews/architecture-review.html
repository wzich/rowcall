Rowcall Architecture Review

July 2026 · Reviewed at commit 336c09d on main

TL;DR

Rowcall's core architectural bet — Python files as the canonical document, with a Python package that owns parsing, validation, planning, and execution — is sound and well executed in rowcall/. The product boundaries described in ADR 0004 and the runtime contract are the right ones for both the open-source local product and a future managed cloud.

The main problems are transitional, not foundational:

  1. A security hole to fix immediately: the local server executes arbitrary Python from HTTP requests and answers cross-origin requests with Access-Control-Allow-Origin: *. Any web page a user visits while Rowcall is running can execute code on their machine.
  2. The old runtime was never deleted. There are three separate implementations that parse Rowcall Python documents and two separate execution runtimes. Roughly 1,500 lines of legacy Python at the repo root duplicate the rowcall package, and the Deno server rewrites Python source with line-based string edits in TypeScript while an unused AST-aware rewriter sits in rowcall/document/rewrite.py. Every behavior change currently has to be made two or three times, and the paths are already drifting (caching, streaming granularity).
  3. No CI. There are good tests on both sides of the language boundary, but nothing runs them automatically.

Recommended sequence: lock down the server and add CI now (both are days, not weeks); finish the runtime migration and delete the legacy paths next (this pays down the single biggest ongoing tax); then invest in run/session modeling, execution isolation, and a shared protocol schema as the on-ramp to cloud and multiplayer.

1. System Overview

The repo contains five layers:

LayerWhereRole
Python package rowcall/ The product core. Authoring API (@node, display, depends_on), AST document parser + validation + run planning (rowcall/document/), stateless executor with value previews and copy handlers (rowcall/runtime/), an NDJSON worker protocol (runtime/worker.py), and the public headless CLI (rowcall validate|run).
Legacy Python scripts runner.py, python_document_loader.py (repo root) Pre-split runtime. runner.py (1,055 lines) is a long-lived session runner speaking a graph-JSON protocol, with the in-memory single-node cache and per-node streaming. python_document_loader.py (494 lines) is a one-shot document parser the server spawns per load/save. Both largely duplicate the package.
Deno/Hono server main.ts, executor.ts, python_worker_client.ts, python_document.ts, document.ts, graph.ts Browser-facing HTTP API: document load/save, graph inspection, three run endpoints with optional SSE streaming, static UI serving. Manages Python subprocesses three different ways and implements Python source rewriting in TypeScript.
React UI app/ui/ React Flow canvas, CodeMirror node editors, TanStack Query for server state, SSE consumption for run progress, and client-side Python parsing via Lezer for output inference.
Launcher & release beta_launcher.ts, release.ts, packaging/, site/ Single-binary launcher (deno compile) that manages a venv under ~/.rowcall, plus Cloudflare Pages/R2 release pipeline and install site.

2. What Is Working Well

  • The document format decision. Keep Real .py files with @node(id=..., outputs=[...]), stable opaque IDs separate from human-readable function names, UI-only .rowcall.json sidecars, and a strict-but-explained validation surface. This is exactly right for the "humans and agents both edit it" goal, and AGENTS.md + the headless CLI make the agent workflow first-class.
  • The rowcall package layering. document/ (parse → validate → plan) is cleanly separated from runtime/ (execute → preview → protocol), models are typed dataclasses, and the CLI and worker are thin shells over the same functions. This is the right kernel to grow.
  • Optimistic concurrency already exists. Documents carry a SHA-256 revision; saves are rejected with stale_document when the file changed on disk. This is a genuinely good foundation for both external (agent) edits and, later, multiplayer reconciliation.
  • Protocol hygiene in the worker. Runtime telemetry is NDJSON on stdout with user stdout/stderr redirected during node execution and even during preview/copy calls, so a hostile __repr__ can't corrupt the protocol. Someone thought about the failure modes here.
  • Reproducibility rules. Rejecting explicit root inputs on source-backed runs (rather than silently ignoring them) keeps "the document is the program" true, which is what makes agent workflows trustworthy.
  • Test coverage habits. Both sides of the language boundary have real tests (Deno tests for document rewriting/streaming/launcher, pytest for parser/rewrite/executor/worker/CLI), including protocol-level worker tests.

3. Findings and Recommendations

Priorities: Now = before more beta users; Next = the next milestone of engineering work; Later = schedule deliberately, mostly pre-cloud.

3.1 Local server is exposed to drive-by code execution Now

What: main.ts adds Access-Control-Allow-Origin: * to every response and answers all preflights permissively, while /run-graph, /run-to-node, and /run-node accept arbitrary Python source (or a graph containing code) and execute it. Binding to 127.0.0.1 does not help: any web page open in the user's browser can fetch("http://127.0.0.1:8000/run-graph", ...), the wildcard CORS headers make the preflight succeed, and the payload runs with the user's full local privileges. PUT /document similarly allows any site to overwrite the user's file.

Change: Remove the wildcard CORS middleware entirely — the UI is served same-origin, so it needs no CORS at all (during vite dev, use a dev-server proxy instead). Additionally validate the Host/Origin headers against the configured hostname to block DNS-rebinding, and consider a per-session bearer token that the launcher embeds in the opened URL — that also cleanly answers "how do non-browser agents authenticate" for the future cloud version.

Impact: Closes a real remote-code-execution vector for every beta tester. Cost is small (the middleware is ~15 lines; the token adds a bit of launcher/UI plumbing).

3.2 Finish the runtime migration; delete the legacy paths Next

What: Three implementations currently understand "what is a Rowcall document": rowcall/document/parser.py (canonical), python_document_loader.py (spawned by the server for every load, save, and render), and the validation embedded in runner.py. Two runtimes execute nodes: runner.py (single-node runs, owns the only cache and the only per-node streaming) and rowcall/runtime/ (graph and run-to-node). runner.py's preview/copy/telemetry half is a near line-for-line duplicate of rowcall/runtime/previews.py. The docs themselves acknowledge this is mid-migration ("single-node execution remains on the legacy session runner until the worker grows cache-aware single-node execution").

Change: Complete the migration in three steps, each shippable:

  1. Add load_document / save_document / render_source operations to the NDJSON worker and route the server's document endpoints through the existing PythonWorkerClient. Delete python_document_loader.py. (Also removes 2–4 process spawns per save.)
  2. Emit per-node events (node_started / node_completed / node_failed) from execute_plan in the worker, restoring the streaming granularity the legacy runner has and the new path lost.
  3. Move the cache-key/session-cache logic from runner.py into RuntimeSession (the class already reserves the seam — it has an unused cache dict), implement source-backed cached single-node runs, switch /run-node over, and delete runner.py plus the PythonRuntimeSession half of executor.ts and the duplicated AsyncEventQueue.

Impact: Removes ~1,500 lines of duplicated Python and several hundred of duplicated TypeScript; eliminates a whole class of drift bugs (preview behavior, validation, streaming shape differing by run type); makes the single-node cache available to CLI/agents later; and shrinks the release surface (compileIncludes drops two files). This is the highest-leverage engineering investment in the repo and should precede any feature that touches execution (caching UX, reactive runs, cancellation).

3.3 Move Python source rewriting out of TypeScript Next

What: When the canvas saves, the server rewrites the user's Python file using line-based string edits in python_document.ts (~1,200 lines: body replacement, node deletion, graph-block regeneration), guided by line ranges reported by the loader, then re-parses the result via a temp file to check it. Meanwhile rowcall/document/rewrite.py implements AST-informed rewrites (update_node_body, update_node_outputs, add_edge, remove_edge) with its own tests — and nothing in the server uses it.

Change: Make the Python package the sole owner of source rewriting. Expose rewrite operations through the worker protocol (natural to do together with 3.2 step 1) and reduce python_document.ts to a thin protocol client. Either extend rewrite.py to cover the structural operations the TS code handles today, or port the TS logic into Python — but end with one implementation.

Impact: Rewriting user-authored Python is the most delicate operation in the product — it can destroy work. One AST-aware implementation, colocated with the parser that defines validity and testable with pytest against real documents, is far safer than two implementations in two languages. It also matters strategically: in the cloud version the rewrite must happen server-side anyway, and "agents edit the file / UI edits the file" converge on the same code path.

3.4 Add CI Now

What: There is no .github/workflows (or any other CI config). Tests exist in three suites (root Deno tests, tests/ pytest, app/ui tests) but nothing runs them on push/PR, there is no repo-wide typecheck task (beta:check covers two entrypoints), and no single command runs everything.

Change: Add a deno task test / deno task check umbrella and a CI workflow running: deno fmt --check, deno lint, deno check over all entrypoints, deno test, pytest, UI typecheck + build. Optionally a scheduled job that exercises release:build so packaging breakage is caught before release day.

Impact: Cheap (a day) and it directly protects the refactors recommended above. Consolidating two runtimes without CI would be needlessly risky.

3.5 Separate fast worker operations from long runs; add cancellation Next

What: The server holds one PythonWorkerClient, and its operations are strictly serialized (operationChain). A long graph run therefore blocks document validation, inspection, and — after 3.2 — document load/save. Worse, user code executes inside the same process as the protocol loop: an infinite loop wedges the worker with no way to cancel (the API has no cancel operation; killing the process is the only remedy and the client only does that on shutdown), and os._exit() or a segfaulting C extension kills the protocol mid-run.

Change: Two-tier worker model: keep one long-lived worker for cheap, pure operations (parse/validate/inspect/plan/rewrite), and execute runs in a child process the worker forks per run (or a small pool). Add cancel_run to the protocol — with process-per-run it's just SIGTERM/SIGKILL — plus optional per-run timeouts.

Impact: The editor stays responsive during runs; users can stop a runaway node (table stakes for a notebook tool — Jupyter has interrupt); crashes are contained to the run. This is also the stepping stone to the "explicit isolation modes" the runtime contract already anticipates, and to per-user execution sandboxes in the cloud. Do it after 3.2 so it's built once, on the surviving runtime.

3.6 Introduce a document-session model in the server Later

What: The server is built around one module-global activeDocumentPath and implicit singleton state (one worker, one legacy session, no run registry). The UI enforces "one run at a time" but the API does not (the TODO in main.ts notes this). Concurrent saves have no mutual exclusion beyond the revision check.

Change: Introduce an explicit DocumentSession object owning: the document path, the worker handle(s), the run registry (IDs, status, cancellation), and the session cache. Route handlers resolve a session rather than touching globals. Keep it single-session initially — the point is the shape, not multi-document support.

Impact: This is the seam that multiplayer, multi-document, and cloud all hang off: "who is editing what, and what is running" becomes addressable state. Doing it early is cheap insurance; doing it after cloud features exist is a rewrite. Sequence it after 3.2/3.5 so you build sessions around the final runtime shape.

3.7 Single-source the cross-language protocol types Later

What: The contract between Deno and Python lives in three loosely coupled places: types.ts (hand-written TS types), ad-hoc dict literals in Python (build_response, worker events), and PythonWorkerEvent typed as [key: string]: unknown with hand-rolled terminal-event lists. The UI additionally re-declares document types in app/ui/src/graph/documentTypes.ts while also importing from ../../../types.ts.

Change: Define the protocol once — JSON Schema files (or TypeSpec) checked into the repo, generating TS types and Python TypedDicts/dataclasses — and validate worker events against it in tests. The protocolVersion field already exists; give it teeth with an explicit compatibility check on both ends.

Impact: Today drift is caught by integration tests, sometimes. In the cloud version, client and server versions will skew across deploys, and a machine-checked, versioned protocol becomes load-bearing. Doing this during 3.2 (when event shapes are already changing) is the cheapest moment.

3.8 Split the two UI monoliths Later

What: App.tsx (1,807 lines) mixes document editing state, name generation, save orchestration, output inference (including the Lezer Python parsing), theme, and layout. InspectorPanel.tsx (2,252 lines) is a similar grab-bag. The API/query layers underneath (api/, query/) are actually well-factored — the problem is concentrated in these two files.

Change: Extract cohesive modules along the seams that already exist: a useDocumentEditing hook (editable document, revisions, save lifecycle), an outputInference.ts module (the Lezer code is already pure functions), node-naming utilities, and Inspector sub-panels per concern (code editor, run results, validation, globals).

Impact: Mostly velocity and reviewability — worth doing opportunistically as these files are touched rather than as a big-bang refactor. It becomes more pressing before multiplayer, which will need presence/remote-edit state threaded through exactly the state management that is currently entangled in App.tsx.

3.9 Smaller observations Opportunistic

  • Duplicated infrastructure in the server: AsyncEventQueue and the spawn/acquire/shutdown subprocess-session machinery exist twice (executor.ts and python_worker_client.ts). Falls out for free with 3.2 step 3.
  • Release config duplication: the compileIncludes list is maintained in both deno.json (beta:compile) and release.ts; they will drift. Generate one from the other.
  • Client-authoritative code on /run-node: the browser sends the full graph JSON (including code) for single-node runs, so what executes can diverge from what's on disk in ways the user can't see. Resolved by making /run-node source-backed in 3.2 step 3.
  • rowcall.egg-info/ is committed (build metadata tracked in git even though a later commit added ignore rules). git rm -r --cached it.
  • File-change detection now has a beta path: the app polls GET /document/status for the app-visible revision, source revision, sidecar revision, and validation issues. Clean external edits auto-reload with a small "Updated from disk" notice; dirty canvas state keeps local edits and warns before reload discards them; temporarily invalid external edits are shown as a neutral "waiting for readable file" state. Proper filesystem watch, operation replay, and merge reconciliation can come later.
  • The UI infers outputs with a third Python parser (Lezer). Acceptable for keystroke-latency hints, but treat it as advisory only and keep the Python parser authoritative; consider eventually asking the worker to confirm inference on save/blur so the two can't silently disagree.

4. Cloud & Multiplayer Readiness

Nothing here argues for building cloud features now, but several current decisions determine how painful cloud will be later. Assessment against that future:

  • Already aligned: Python-file-as-truth plus content-hash revisions is a strong base for sync and conflict detection. The parse/plan/execute kernel being a pure Python package means the cloud runtime can be the same code in a container. The explicit-outputs/copied-inputs node contract is exactly what makes per-node caching, distributed execution, and "branch from a shared node" tractable later.
  • Needs the seams recommended above: multiplayer needs a document session (3.6), a run registry with cancellation (3.5), a versioned protocol (3.7), and an auth story (the token from 3.1 is the embryo of it). None of these need cloud infrastructure today — they need the local architecture to stop assuming "one global document, one anonymous user, one implicit run."
  • One design question to settle before multiplayer work starts: the unit of collaborative editing. The current save model is whole-document (render + revision check), which forces last-writer-wins at file granularity. The natural unit for Rowcall is probably the node (body edits) plus the graph structure (add/remove node/edge) — which is exactly the operation vocabulary rewrite.py already defines. Consolidating rewriting into those operations (3.3) quietly becomes your operational-transform vocabulary later; that's a strong reason to prefer operation-shaped rewrite APIs over "replace the whole source" when doing 3.3.

6. Assumptions Made in This Review

  • The beta audience is individual practitioners running locally; hence "Now" weights local security and release safety over scalability.
  • The migration direction stated in ADR 0004 and the runtime contract (Python package as the canonical runtime, legacy paths temporary) is still intended. If instead the legacy runner is meant to live on, findings 3.2/3.3 change from "finish and delete" to "define the drift boundary" — but I'd argue strongly for finish-and-delete.
  • TypeScript-language documents (mentioned in product scope) are far enough out that the runtime abstraction shouldn't be generalized for them yet; the worker protocol (3.7) is the layer to keep language-neutral when the time comes.
