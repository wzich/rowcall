Architecture review · current main

Preserve the core. Harden the seams.

Rowcall has a coherent local-first architecture and an unusually good foundation for human and agent use. The shortest path to broader distribution is not a rewrite: it is correctness under iteration, crash-safe persistence, trustworthy releases, and one discoverable, versioned semantic contract around the Python core.

01 / Executive assessment

A sound architecture at an alpha maturity level

The product model is stronger than the release and operational envelope around it. That is a favorable problem: the expensive conceptual choices are mostly right.

Central recommendation: define one versioned semantic capability layer for inspect, edit, validate, plan, run, and observe. The canvas, an agent-facing CLI, and a future collaboration service should be adapters over that layer. Keep ordinary Python as the durable local artifact; do not force agents through browser gestures.

02 / Current system

Two authoring paths, one Python core

This is the most important architectural success in the repository. Humans and agents enter differently, but computation converges before validation and execution.

Edit path

Optimistic semantic operations

  1. The UI loads a parsed document and composite source/sidecar revision.
  2. Graph gestures update an optimistic working copy and queue typed operations.
  3. Save sends the operations with a base revision.
  4. Python rewrites and validates candidate source.
  5. Deno rechecks locked file contents, writes source and sidecar, then reparses.

Run path

Source-backed worker execution

  1. The UI flushes pending operations before a run.
  2. A long-lived Python worker parses and topologically plans the graph.
  3. Globals run once; nodes run sequentially in fresh dictionaries.
  4. Rich Python values stay inside the process; bounded previews cross the API.
  5. Plans and node completion events stream to the browser over SSE.

04 / Priority findings

The core is ready for hardening, not complacency

P0 means before inviting unknown users or publishing the repository. P1 belongs in the public-alpha cycle. P2 is a conscious scaling or product decision, not immediate release work.

P0 · correctness

Iterative runs can be confidently wrong

The long-lived worker restores its working directory and sys.path, but does not reload document-local modules. Editing a sibling helper module can therefore leave a later run using the old module from sys.modules. Single-node cache keys cover code, globals, root inputs, and upstream keys, but not document path, environment identity, or files read by a root node.

The parser also silently accepts near-miss documents as valid zero-node graphs. Verified examples include ordinary x = 1, an async function decorated with @node, and a function decorated with @rowcall.node. A false green is especially dangerous to an agent.

Recommendation: add explicit format detection and near-miss diagnostics; validate raw-source IDs, outputs, and duplicate edges; define document-local import freshness; namespace caches by document/session/environment; expose the cache fingerprint and a clear-cache reason. Treat external data dependencies as declared inputs or documented cache escape hatches.
parser.py:88–119 · validation.py:10–18 · executor.py:152–206, 233–245 · session.py:17–27
P0 · data safety

Save is concurrency-aware but not crash-atomic

Revision checks and file locks are thoughtful, but the live Python file is truncated and rewritten in place before the sidecar is updated. Caught exceptions trigger best-effort rollback; a process kill, power loss, or disk failure can leave a partial source or a mismatched source/sidecar pair.

The browser-generated clientBatchId is accepted and echoed but ignored by persistence, so a lost successful response cannot be retried idempotently. Unsaved operations exist only in React memory, with no draft recovery or navigation guard.

Recommendation: write each artifact to a same-directory temporary file and fsync it, but do not treat two atomic renames as a transaction. Commit a versioned Python/sidecar generation through a journal or atomic generation pointer, fsync the directory, and define the recovery protocol. Preserve file modes, make batch IDs real idempotency keys, and add IndexedDB draft recovery, undo/redo, and close protection. Test every write failure point.
python_document.ts:137–160, 597–741 · App.tsx:243–320
P0 · resource safety

Trusted local execution is not yet bounded local execution

User code runs with the selected Python process's ordinary filesystem, network, process, and environment privileges. That is appropriate for an explicitly trusted local document, but there is no run timeout, memory bound, output cap, or cache budget. Stdout is retained in a StringIO and again in output events; traces can duplicate it. Expensive repr and deepcopy calls happen before post-hoc truncation.

Recommendation: state the trusted-code boundary prominently; cap stdout, stderr, events, previews, cache entries, and total cached bytes; report truncation; add wall-time cancellation and process-group cleanup. Never reuse this worker as a multi-tenant sandbox.
executor.py:438–579 · previews.py:276–344 · python_worker_client.ts:431–466
P0 · installation

Concurrent launches can race while rewriting shared installed assets

Every packaged launch materializes UI and Python assets into one shared ~/.rowcall/bundled directory. Copying a directory first recursively deletes the destination, and managed virtual-environment creation and package installation have no interprocess lock. Two Rowcall instances can interfere with each other.

Recommendation: use immutable, content-addressed runtime directories, materialize into a temporary directory, atomically promote, and lock managed environment creation. Running processes should retain their version; cleanup should remove only provably unused versions.
beta_paths.ts:15–30 · beta_launcher.ts:706–835, 1285–1302
P0 · public release

The release channel proves corruption, not publisher identity

The installer and compiled launcher are real, but the release is macOS-only, unsigned, and manually built/deployed. Binary and checksum come from the same publisher endpoint. Mutable latest objects are consumed directly, versioned objects can be overwritten, update is unimplemented, and the managed starter environment installs unpinned pandas and Polars from the live package index.

The artifact is also a launcher, not a hermetic data-science binary: it still requires Python 3.10 or newer and may invoke pip in managed mode. That is a reasonable product choice, but it should be named honestly.

Recommendation: build from clean signed tags with a pinned toolchain; refuse version reuse; code-sign and notarize; publish a signed manifest, SBOM, provenance, and immutable assets; lock managed dependencies with hashes; test install, launch, validate, run, upgrade, rollback, and both architectures on actual macOS runners.
release.ts:20–31, 82–183 · packaging/install.sh:7–61 · requirements-alpha.txt · site/index.html:229–231
P0 · before public repo

Open-source policy and project identity are undefined

There is no tracked license, security policy, contribution guide, code of conduct, changelog, governance document, or third-party notice. Python package metadata is minimal. The pip-installed rowcall command exposes only validate/run while the binary of the same name exposes the full launcher, creating an avoidable public contract ambiguity.

Recommendation: choose the license and commercial boundary before visibility creates expectations. Add SECURITY, CONTRIBUTING, support/release policy, notices, DCO or intentional CLA policy, package metadata, and a clear statement about which CLI is the product contract.
pyproject.toml:1–15 · rowcall/cli.py:15–20 · beta_launcher.ts:157–217
P1 · diagnostics

Tracebacks can point at shifted source lines

Runtime globals are assembled by removing excluded source lines, while each node is compiled as an extracted fragment beginning at line one. The traceback filename is useful, but its reported line can identify the wrong statement in the original document—costly friction for humans and especially for agents applying a targeted repair.

Recommendation: preserve original line positions with blank padding or adjusted AST locations, and expose structured traceback frames remapped to original source spans. Add tests that assert exact document line numbers for failures in globals and nodes.
parser.py:447–492, 575–608 · executor.py:516–540
P1 · contracts

The intended protocol is good, but its types already drift

Operations, validation issues, run errors, and document models are repeated across Python, root TypeScript, UI TypeScript, and prose. For example, Python emits run error kinds that are not represented in the TypeScript union. Worker messages carry a protocol version, but incoming versions are not enforced. A large legacy full-document decoder appears unused in the production path.

Recommendation: adopt one versioned schema source for documents, operations, diagnostics, worker messages, run events, and capabilities; generate or validate bindings on both sides. Add compatibility fixtures and migrations before a public v1 claim.
document.ts:445–825 · types.ts:67–128 · runtimeTypes.ts:1–31 · worker.py:56–70 · python_worker_client.ts:118–127, 214–219
P1 · application structure

Singletons and UI controllers will resist collaboration

main.ts stores active document and security state in module globals. executor.ts owns one global worker. The 2,364-line App.tsx coordinates server snapshots, optimistic commands, external changes, saves, execution, graph derivation, and rendering. The 2,208-line inspector similarly mixes editing, result models, traces, and presentation.

Recommendation: introduce a composition root with injected DocumentRepository, ExecutionBroker, auth, and event sink. Extract a document command store/reducer, save coordinator, external-change reconciler, and execution coordinator before realtime state is added.
main.ts:27–34 · executor.ts:38 · App.tsx:102–1499 · InspectorPanel.tsx:1–2208
P1 · conflicts

Stale writes are rejected, but disjoint work cannot be replayed

One composite hash correctly protects source and sidecar changes, but a layout move can conflict with unrelated code. When local edits exist, the recovery action is reload and discard. Graph operations already contain enough intent to do better.

Recommendation: on a 409, fetch the newest revision and replay pending operations. Commit disjoint node-field edits automatically; surface a conflict only for the same field, deleted identity, invalid graph, or code overlap. Preserve separate computational and presentation revision dimensions.
python_document.ts:421–466 · App.tsx:419–490, 1052–1141
P1 · security posture

Current routes are protected, but future routes fail open

Loopback default, random token, Host/Origin checks, and URL scrubbing are good. However, token enforcement enumerates protected route prefixes; a newly added API route omitted from the list becomes unauthenticated. The token is printed in the startup URL and packaged server output is appended to an unbounded local log. Arbitrary non-loopback binding remains plain HTTP.

Recommendation: mount a fail-closed authenticated /api/v1 router and allowlist only exact static GETs. Redact tokens, bound and protect log files, test every registered route, and require an explicit remote-listen acknowledgment with TLS guidance.
main.ts:170–243 · auth.ts:23–48 · beta_launcher.ts:923–960, 1220–1242
P1 · product quality

The shipped experience is under-tested at its real boundaries

Unit and integration coverage is strong for the codebase's size, but CI is one Ubuntu/Python 3.11 job. There is no browser end-to-end suite, packaged-binary or installer smoke test, multi-tab conflict test, concurrent extraction test, or injected crash-write test. The Vite proxy also omits /runtime/python, a route the UI calls in development.

Recommendation: add Python 3.10 through the highest supported version, exact Deno, macOS artifact tests, browser flows for edit/save/external edit/run/cancel, parser fuzz/property tests, and fault/concurrency tests. Proxy an authenticated API prefix rather than individual routes.
.github/workflows/ci.yml · app/ui/deno.json:3–8 · vite.config.ts:9–19
P1 · human UX

The editor is desktop-shaped and often silent about rejected actions

The inspector has a 520-pixel minimum while reserving at least 360 pixels for the canvas, and both remain side by side. Some custom-node graph edits simply return without explaining why; invalid connections are usually discovered only on save.

Recommendation: add a phone/tablet canvas vs. inspector switch or bottom sheet, larger touch targets, and a graph outline. Mirror cheap validation in the client for fast feedback while keeping Python authoritative.
InspectorPanel.tsx:22–48 · App.tsx:738–977, 1432–1494 · Canvas.tsx:212–218
P2 · deliberate evolution

Freeze or version whole-node edge semantics consciously

Today every output from every direct parent is flattened into the child's parameter scope. This simplicity is excellent for small graphs, but output conflicts, signature cascades, and inability to select or alias ports will become more visible as graphs grow.

Recommendation: do not complicate the alpha format prematurely. Before 1.0, decide whether v1 permanently means whole-node data edges or whether a future version adds selective bindings, aliases, or control-only dependencies.
runtime contract · validation.py:135–186 · rewrite.py:680–735

05 / Humans and agents

Semantic parity, not interaction parity

An agent should not have to pan a canvas or click a handle. It should be able to discover and invoke the same graph capabilities with machine-readable preconditions and results.

Design principle: the human canvas and an agent-facing CLI should be peers. Both inspect the same revision, submit the same semantic changes when appropriate, and validate and run through the same Python core. Direct Python editing remains a first-class local escape hatch.

Low-cost opportunity

Much of the agent API already exists internally

The worker already implements inspect, validate, plan, render, candidate validation, semantic apply, graph run, targeted run, and cache clear. The work is to expose, version, document, and test those capabilities—not invent a second automation system.

Discovery

Make success mean the intended graph was understood

Capabilities should state supported syntax and operation preconditions. Inspection should surface warnings for near-miss decorators and unsupported forms, not silently report a valid empty graph. 

rowcall capabilities --json
rowcall inspect my-project --json
rowcall plan my-project --to clean_data --json
rowcall apply my-project --base-revision REV --operations ops.json --dry-run --diff
rowcall run my-project --node clean_data --events ndjson
rowcall run my-project --to clean_data --json --trace

Do not make MCP the core API. An MCP server could be a useful adapter for discovery and tool invocation, but it should wrap the same CLI/application protocol used by the web editor and other automation. The durable contract should not depend on one agent ecosystem.

06 / Distribution and open source

Ship a trustworthy launcher, then publicize a trustworthy project

The binary and open-source tracks share engineering, but their gates are different. Signing and crash safety unlock distribution; governance and compatibility unlock a healthy public repository.

What ships today

A compiled launcher with an external Python runtime

  • macOS arm64 and x64 artifacts, currently about 67 MB and 79 MB locally
  • Embedded React UI and Rowcall Python package
  • User-selected Python by default
  • Optional managed venv that installs starter packages
  • Local loopback web server with random bearer token

This hybrid is sensible for data-science package compatibility. Avoid promising a hermetic “single binary” unless Python itself is later bundled.

Recommended posture

Keep flexibility; make the managed path deterministic

  • Continue to respect an activated user environment
  • Lock and hash the managed starter environment
  • Include environment identity in doctor, cache, and run provenance
  • Use versioned content-addressed installed assets
  • Add a real signed update and rollback flow
  • Describe Python and network requirements before installation
Open-source core

Good candidates to keep public

  • Python document format, parser, validator, planner, rewrites, previews, and local runtime
  • Versioned schemas and compatibility tests
  • Headless CLI and agent adapters
  • Local server, web editor, and local filesystem/worker adapters
  • Examples, developer tooling, and release verification logic
Commercial service

Natural managed differentiation

  • Organizations, identity, ACLs, SSO, policy, and audit
  • Durable project history, realtime presence, and collaboration gateway
  • Run scheduling, isolated hosted environments, secrets, quotas, and artifact retention
  • Enterprise connectors, compliance, reliability, support, and billing

Suggested open-source posture: a permissive core such as Apache-2.0 fits a strategy where trust, adoption, local extensibility, and an ecosystem matter, while hosted operations and collaboration carry commercial value. AGPL is a legitimate reciprocity choice with a different adoption profile. Make this an explicit business/legal decision; do not drift into an accidental license. Protect the Rowcall name and marks separately from code licensing.

Avoid a premature repository split. First introduce clear internal modules and interfaces inside the monorepo. Physical packages or services should follow independent release, ownership, or deployment needs—not anticipate them. The first valuable split is contracts from adapters, and document compilation from arbitrary execution.

Local mode

Files remain canonical

FilesystemDocumentRepository loads, watches, applies, and atomically checkpoints Python plus sidecar. Direct human and agent file edits remain supported. External changes create a new revision and queued semantic edits are replayed when safe.

Managed mode

A durable revision is canonical

Persist a revision containing Python source, sidecar metadata, and format version. An operation log and text collaboration state coordinate edits, authorship, and history; the parsed graph remains derived. Agents submit base-revision operations or source patches through the same validation/commit boundary.

Avoid three sources of truth. Do not let raw Python, a structured graph document, and a CRDT each become independently authoritative. Python source plus sidecar should remain the portable executable snapshot. Collaboration operations are the coordination and audit mechanism that produces a new valid snapshot; the graph is derived from it.

Run model

Execute immutable revisions, not “latest”

  • POST /runs returns a durable run ID
  • Events can be reconnected and replayed
  • Run records include source revision, environment hash, runtime versions, actor, timestamps, and per-node timing/cache status
  • Outputs and artifacts are stored separately from transient UI state
Isolation

Execution is the commercial system's hardest boundary

  • Ephemeral worker per tenant/workspace/session policy
  • Unprivileged identity and scoped workspace mount
  • Read-only base, no platform credentials, secrets injected narrowly
  • CPU, memory, PIDs, disk, wall time, output, and network quotas
  • Whole process-group/container cancellation and cleanup

Lowest-risk commercial sequence: host projects, revisions, identity, and collaboration first while execution remains on a signed local Rowcall runner. This leverages the existing user-environment architecture and can keep sensitive data local. Add managed isolated runners when environment specifications, artifacts, secrets, quotas, and run provenance are mature. Make “run locally” versus “run on shared managed compute” an explicit choice.

08 / Recommended sequence

Four gates, in dependency order

The sequence intentionally builds reliability and a common contract before realtime collaboration. Those investments pay off for local users and agents even if the managed product changes.

Gate 0
Broader local beta

Correctness, durability, and installation trust

  • Diagnose near-miss/empty graphs; validate raw-source IDs, outputs, and edges; preserve traceback line positions.
  • Fix document-local module freshness and namespace caches by document/session/environment.
  • Make source/sidecar saves crash-safe; add batch idempotency and draft recovery.
  • Bound output, cache, and runtime resources; state the trusted-code model.
  • Make bundled assets immutable and concurrent-launch-safe.
  • Code-sign/notarize, lock managed dependencies, and automate macOS install/upgrade smoke tests.
  • Fail closed on API auth, redact tokens, rotate logs, and guard non-loopback mode.
Gate 1
Public open-source alpha

Stable contracts and a contributor-ready project

  • Choose license and trademark posture; add security, contribution, conduct, support, and release policies.
  • Publish versioned schemas and compatibility fixtures for document operations, diagnostics, runs, and events.
  • Expose inspect, plan, capabilities, apply/dry-run/diff, and event-streaming CLI commands.
  • Unify the binary and Python-package command story.
  • Add Python/toolchain matrices, browser E2E, parser fuzzing, and write/concurrency fault tests.
  • Extract document/session coordinators from React and app dependencies from module globals.
Gate 2
Collaboration foundation

Durable revisions before multiplayer polish

  • Define DocumentRepository, PythonSourceAdapter, ExecutionBroker, IdentityPolicy, and event/audit interfaces.
  • Give projects and documents stable IDs; persist actor, base/result revision, sequence, and idempotency key.
  • Replay/rebase disjoint operations across tabs, filesystem edits, and agents.
  • Introduce durable runs tied to immutable document and environment revisions.
  • Separate computational source revision from presentation revision and execution cache identity.
Gate 3
Managed multiplayer

Realtime collaboration and isolated execution

  • Add workspace identity, roles, ACLs, audit, and scoped agent credentials.
  • Broadcast committed graph operations and ephemeral presence over a collaboration channel.
  • Begin with local runners; make shared run ownership and result visibility explicit.
  • Add hosted sandbox workers, secrets, quotas, artifacts, replayable run events, and operational controls.
  • Adopt text CRDTs only for fields where real concurrent editing justifies them.
Decide now
  • Python source and sidecar ownership
  • Trusted local vs. isolated managed execution
  • Versioned semantic capability contract
  • Release signing and dependency reproducibility
  • Open-source license and commercial seam
Defer deliberately
  • CRDT vendor/library choice
  • Kubernetes or microservice topology
  • Database and queue implementation
  • General plugin system and extra languages
  • Complex port semantics before evidence from larger graphs

Notable current contract facts
  • Rowcall source format is implicitly v1; the app model and worker protocol carry version 1, but the Python file has no explicit format marker.
  • All outputs from a direct upstream node become inputs to the downstream node; edges are node-to-node, not port-to-port.
  • Full and upstream runs refresh the cache; exact single-node execution requires valid cached upstream objects.
  • App writes are operation-shaped and revision-checked. Direct file writes remain authoritative and are detected by four-second polling.
  • The current server accepts one active Python document and uses one serialized long-lived execution worker.
  • The local browser token is stripped from the visible URL after storage, but the startup URL itself is logged.

Bottom line: Rowcall does not need a new core architecture before broader use. It needs its existing core turned into a reliable product and a public contract. The highest-leverage next move is a hardening milestone that simultaneously fixes iteration correctness, crash safety, release trust, and agent discoverability.
